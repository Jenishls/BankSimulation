# Banking Console

Banking Console is a .NET 10 banking-domain application built with ASP.NET Core,
Entity Framework Core, and SQL Server. It models customers, configurable banking
products, customer and office accounts, double-entry transactions, and daily
interest calculation, tax, and posting.

The application exposes a health endpoint plus customer and product CRUD
endpoints. Account, transaction, and interest operations are implemented in the
service layer and covered by automated tests, but they are not yet exposed
through HTTP endpoints.

## Main features

- One `Product` model configures savings, term-deposit, and loan products.
- One `CustomerAccount` model supports all three customer product types.
- `OfficeAccount` represents internal income, expense, tax-payable, suspense,
  and cash accounts.
- Account numbers are generated centrally by
  `AccountNumberGeneratorService`.
- Transactions use balanced debit and credit ledger entries.
- Interest is calculated daily using simple interest.
- Posting schedules support frequency-end, maturity, and a configured date.
- Credit interest can be subject to withholding tax.
- Transaction idempotency protects interest and tax posting from duplicates.
- EF Core migrations define the SQL Server schema.

## Domain model

### Products

A single `Product` class creates different products through `ProductType`:

| Product type | Interest flow | Product-specific account data |
| --- | --- | --- |
| `SAVING` | Credit | Opening balance |
| `TERM` | Credit | Principal, tenure, funding account, maturity settlement account |
| `LOAN` | Debit | Principal, tenure, disbursement account, repayment account, installments |

Every product identifies:

- An interest office account.
- A tax-payable office account.
- An annual interest rate.
- A tax rate.
- One or more interest-posting policies.
- Whether interest posts to the source account or an applicable linked account.

Savings and term products use an `EXPENSE` office account for interest. Loan
products use an `INCOME` office account. The tax account must be a
`TAX_PAYABLE` office account in the same branch as the product.

Withholding tax is supported only for credit-interest products. Loan products
therefore cannot be configured with a positive tax rate.

### Accounts

There are two persisted account types:

- `CustomerAccount` belongs to a customer and product. Its `ProductType`
  determines whether it behaves as a savings, term, or loan account.
- `OfficeAccount` is an internal ledger account associated with a branch and an
  `OfficeAccountType`.

Term and loan accounts use linked savings accounts for settlement:

- A term account requires funding and maturity-settlement accounts.
- A loan account requires disbursement and repayment accounts.
- Linked accounts must be active savings accounts owned by the same customer.

### Account-number generation

Account numbers are generated by `AccountNumberGeneratorService`; customers and
offices do not generate or store number-generation rules.

The generated format is:

```text
{BRANCH_CODE}{TYPE_CODE}{12_CHARACTER_UNIQUE_VALUE}
```

Type codes are `OF` for office, `SA` for savings, `TD` for term deposit, and
`LA` for loan accounts.

## Interest engine

`InterestEngine.ExecuteAsync(processingDate)` coordinates the daily process:

1. Load all products.
2. Load active customer accounts for each product.
3. Calculate and accrue daily simple interest once per account and date.
4. Calculate withholding tax for credit interest.
5. Resolve whether posting is due.
6. Post tax first, followed by gross interest.
7. Persist account accrual and posting state.

Daily interest is rounded to two decimal places:

```text
daily interest = balance × (annual rate / 100) / 365
```

Savings and term products calculate interest on the account balance. Loans
calculate interest on outstanding principal.

Posting can use the source account or, when
`PostInterestToLinkedAccount` is enabled:

- A term product posts to its maturity-settlement account.
- A loan product posts to its repayment account.

### Interest and tax entries

For credit interest with tax, the engine creates two separate transactions in
this order:

1. Tax transaction: debit the posting customer account and credit the product's
   tax-payable office account.
2. Interest transaction: credit the posting customer account with gross
   interest and debit the product's interest-expense office account.

The customer's net increase is therefore gross interest minus tax.

For loan interest, no withholding tax is imposed. The interest transaction
debits the posting customer account and credits the product's interest-income
office account.

## Project structure

```text
BankingConsole/
├── Common/                  Shared results and domain exceptions
├── Contracts/               Service request contracts
├── DB/                      DbContext, unit of work, and migrations
├── Factories/               Customer, product, and account construction
├── Middleware/              Central exception handling
├── Models/                  Domain entities, creation data, and enums
├── Repository/              EF Core repositories
├── Services/                Application services
│   └── Interest/            Calculation, due resolution, posting, and tax
├── BankingConsole.Tests/    xUnit test project
├── Program.cs               Dependency injection and HTTP pipeline
└── appsettings.json         Local configuration
```

## Prerequisites

- [.NET 10 SDK](https://dotnet.microsoft.com/download/dotnet/10.0)
- SQL Server or SQL Server Express
- EF Core CLI:

```powershell
dotnet tool install --global dotnet-ef
```

Use an EF CLI version compatible with the EF Core 10 runtime used by the
project.

## Configuration

The default configuration expects a local SQL Server database:

```json
{
  "ConnectionStrings": {
    "DefaultConnection": "Server=localhost;Database=BankingConsoleDb;Trusted_Connection=True;TrustServerCertificate=True;"
  }
}
```

For machine-specific or sensitive settings, override this connection string
with environment variables or an uncommitted development settings file instead
of committing credentials.

For example:

```powershell
$env:ConnectionStrings__DefaultConnection = "YOUR_CONNECTION_STRING"
```

## Build and run

Restore dependencies and build:

```powershell
dotnet restore
dotnet build
```

Apply the existing database migration:

```powershell
dotnet ef database update --context AppDbContext
```

Run the application:

```powershell
dotnet run --project BankingConsole.csproj
```

Use the HTTP URL printed by ASP.NET Core to check the application:

```text
GET /health
```

The response is:

```json
{
  "status": "Healthy"
}
```

Customer operations are available under `/api/customers`, and product
operations are available under `/api/products`.

## Database migrations

The initial migration and current model snapshot are stored in
`DB/Migrations`.

After changing entities or `AppDbContext`, create a migration with:

```powershell
dotnet ef migrations add MigrationName --context AppDbContext --output-dir DB/Migrations
```

Check whether the model has uncommitted schema changes:

```powershell
dotnet ef migrations has-pending-model-changes --context AppDbContext
```

Review every generated migration before applying it, especially changes that
drop columns, tables, or relationships.

## Tests

Run the complete test suite:

```powershell
dotnet test BankingConsole.Tests/BankingConsole.Tests.csproj
```

The tests cover product and account construction, account-number generation,
the EF Core model, transactions and ledger entries, interest calculation,
posting, tax, and the interest engine.

## Customer API

The customer controller exposes:

- `GET /api/customers`
- `GET /api/customers/{customerId}`
- `POST /api/customers`
- `PUT /api/customers/{customerId}`
- `DELETE /api/customers/{customerId}`

`POST` and `PUT` accept an optional `Idempotency-Key` GUID header. When it is
omitted, the API generates one and returns it in the response header. `PUT` also
accepts an optional `X-Performed-By` header for the customer audit record.

## Product API

The product controller exposes:

- `GET /api/products`
- `GET /api/products/{productId}`
- `POST /api/products`
- `PUT /api/products/{productId}`
- `DELETE /api/products/{productId}`

`PUT` uses `ProductCreationData` as a complete replacement payload. A product
cannot change type or be deleted while customer accounts reference it.

Account, transaction, and interest endpoints still need to be exposed to make
this a complete HTTP banking API. The interest engine is particularly suited to
a scheduled daily background job.
